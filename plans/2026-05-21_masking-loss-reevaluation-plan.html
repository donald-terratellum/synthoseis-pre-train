Masking Loss Re-evaluation Plan

Date: 2026-05-21
Scope: Training pipeline masking behavior review and remediation, with MONAI 1.0.0 API/pattern comparison.

Objective

Re-evaluate whether non-standard masking and weighting in loss computation is the primary cause of weak training improvements, and isolate masking effects from architecture and data quality factors.

Required Outcomes

  • Analyze mask usage overall in the training pipeline.
  • Analyze mask usage inside loss computation.
  • Analyze mask impact on back-propagation and gradient flow.
  • Analyze mask usage that is restricted to printed stats, diagnostics, and QC plots.
  • Compare current pipeline behavior to MONAI 1.0.0 training/loss masking patterns.

Constraints and Process Rules

  • Create and work on a new branch from local main.
  • Execute work in explicit phases.
  • Each phase must include constructive critic code review, tests written or updated, tests passing, and a git commit before proceeding.
  • Final phase must include end-to-end review, end-to-end testing, final commit, and a session summary in .agentic-docs as markdown and html.

Phase Plan

Phase 0: Branch, Baseline, and Reproducibility Lock

Purpose: establish a stable reference so all mask changes are measurable.

  • Create branch from local main: feat/masking-loss-reevaluation.
  • Freeze baseline config (dataset slice, seeds, epochs, loss type, mask params).
  • Capture baseline metrics and representative QC artifacts.
  • Record exact reproducibility commands.

Gate: targeted mask/loss tests and smoke run pass, then commit.

Phase 1: Ground-truth Mask Usage Mapping

Purpose: produce a complete, unambiguous mask map from data loading to reporting.

  • Map where masks are created, transformed, expanded, and combined.
  • Map exact semantics at each boundary (True/False meaning).
  • Map all mask call sites in training logic.
  • Separate training-path usage from diagnostics-only usage.

Deliverables: markdown and html reports in plans folder.

Gate: targeted semantics tests pass, then commit.

Phase 2: Loss and Gradient Path Validation

Purpose: verify whether masking changes optimization behavior in unintended ways.

  • Trace all loss branches with mask inputs.
  • Validate reduction and normalization under variable valid-voxel counts.
  • Validate masked vs unmasked gradient behavior.
  • Validate sparse and empty-mask edge-case handling.

Gate: targeted routing/gradient stability tests pass, then commit.

Phase 3: MONAI 1.0.0 API/Pattern Comparison

Purpose: compare existing approach to MONAI-standard masked loss patterns and training/evaluation separation practices.

  • Produce gap table: current behavior vs MONAI pattern.
  • Rank gaps by training-risk severity.
  • Define minimal and safe remediation order.

Gate: remediation tests pass, then commit.

Phase 4: Mask Remediation Implementation

Purpose: implement only high-value mask-related fixes first.

  • Harden mask semantics and loss dispatch logic.
  • Isolate diagnostics-only masking from training hot path.
  • Remove redundant per-batch diagnostic loss recomputation from critical path when safe.

Gate: targeted tests and train epoch smoke pass, then commit.

Phase 5: End-to-End Validation and Session Closeout

Purpose: prove final integrated behavior and preserve traceability.

  • Run end-to-end smoke plus selected convergence checks.
  • Validate no regression relative to baseline metric trends.
  • Perform final constructive critic review.
  • Write final summary in .agentic-docs (markdown and html).

Gate: end-to-end checks pass, then final commit.

Proposed Targeted Test Matrix

  • tests/test_losses.py
  • tests/test_masking_sampling.py
  • tests/test_loss_cluster_aware.py
  • tests/test_train_epoch_smoke.py
  • New tests during execution: test_compute_masked_loss_routing.py, test_mask_gradient_flow.py, test_mask_semantics_contract.py, test_diagnostics_no_grad_separation.py

Key Risks to Monitor

  • Inconsistent mask semantics across modules.
  • Loss routing fallback changing tensor-shape assumptions.
  • Sparse-mask numeric instability in local-window losses.
  • Diagnostic logic accidentally affecting training behavior or throughput.
Confidence strategy: keep phase deltas small, require tests and commits per phase, use fail-fast behavior for unsupported mask/loss contracts, and defer non-mask architecture/data interventions unless mask analysis proves insufficient.

Open Questions to Ask During Execution If Needed

  • Minimum acceptable metric drift threshold between phases.
  • Whether to escalate to full test suite at high-risk phase boundaries.
